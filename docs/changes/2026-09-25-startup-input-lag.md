# 启动卡顿与输入延迟：命令移出 UI 主线程

## 现象

应用一打开要卡一阵才有反应；分析进行中打字时，文字要停顿一下才出现在输入框。点击发送后要等任务归属模型返回，消息才出现、输入框才清空。

## 根因

1. **同步命令跑在主线程**。Tauri 2 中未标 `async` 的 `#[tauri::command]` 在主线程执行，而 Windows 上 WebView2 的输入事件也由主线程派发。本项目约 89 个命令都是同步的，任何一次慢命令（读凭据库、跑子进程、等 SQLite 锁）都会冻住整个窗口。前端还有多条周期轮询（OAuth 状态 2s、Agent 任务 0.8–1.2s、素材页 1.5s、分析门 1.5s），所以卡顿会周期性出现在打字时。
2. **启动时重复哈希约 700 MB 模型权重**。`initialize_local_store` 的自动下载检查、`get_runtime_model_status` 的基线刷新和状态快照各把 BGE/CLIP 三个 `model.onnx` 整文件读入内存并 SHA-256，一次启动约读 2 GB，且都在主线程。
3. **每次打开连接都重跑迁移**。约 164 处 `open_connection` 每次都执行完整 `migrate`，其中 `UPDATE operation_logs ...` 与 `INSERT OR IGNORE INTO schema_migrations` 是写语句，需要写锁；后台分析持有写事务时会按 `busy_timeout` 最多等 5 秒。

## 变更

- 所有同步命令改为 `#[tauri::command(async)]`，在异步运行时线程执行；函数签名、参数和返回值不变，前端 `invoke` 契约不变。
- `runtime_models::artifact_ready_on_disk` 改为流式哈希，并按「路径 + 大小 + 修改时间」缓存本进程已校验通过的文件；文件被替换后元数据变化会重新校验，未通过的结果不缓存。
- `db::open_connection` 每个数据库文件在本进程成功迁移一次；迁移失败时下次打开重试。
- 发送消息时先在对话区显示用户消息（标「发送中…」）并清空输入框，再等任务归属模型请求；落库后替换为真实消息。落库前取消或失败会移除该消息并把原文放回输入框（输入框已有新内容则不覆盖）。

## 未改

- 前端输入状态仍在 `App` 中，每次按键会重渲染整棵组件树；目前不是主要瓶颈，后续若仍有输入延迟再下沉到 composer。
- 发行检查仍会启动 FFmpeg/FFprobe/Tesseract/Python 子进程，但已不在主线程。

## 验证
