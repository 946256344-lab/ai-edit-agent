# 策划校准（任务 4b）

本分支只改盘点、体裁、策划与 planning-only 评测，不接 generate_storyboard，不改任务 3 底线规则、选镜关系或 Phase 4，不启动窗口/开发服务器，不推送合并。

## 接口与行为

- planning-only 对实际体裁调用任务 3 `evaluate`，未知不放行；支持复用上游单次真实核验快照与显式合格窗，收窄后重新封印。每例保存 `eligibility.json` 和 `eligible-evidence.json`，报告合格数；零合格是 `gap_only`，不记成服务失败。
- `Inventory.requirements[]` 保存本请求临时画面需求、必需性与原锚点引用。请求提取枚举 `visual/editing_instruction/narration_expression`，代码只留具体画面，不把无配音、强结尾或抽象口号当缺素材。每个需求逐片段核验，每六个固定片段键组成独立并发请求，严格 Schema 强制全部真假判定，代码绑定身份并单独枚举每键锚点，消除跨批索引误配和检索漏项；缺口只来自零有效支持需求。策划自由缺口文本在审核前被代码纠正，支持过的画面不能再被宣称缺失。没有支持的卖点仍须独立语义审核，不能靠合法 ID 放行。模型伪造因果 ID/锚点被拒绝并记 `rejectedCausalLinks`，不会用于完整链或导致宣传盘点运行失败。
- `audit_rules(genre)` 是代码参数。宣传只校验卖点直证、气氛支持位置、标题/品牌与数字来源，其全局审核 Schema 没有因果字段；叙事才审核真实因果/转折；花絮审核真实瞬间，代码按预算检查空镜 ≤20%，缺空镜事实保持未知并拒绝。直观可见主体/动作/场景描述属于直证，不能要求每个宣传镜头建立因果。
- 自动 AI 提出需求意图，代码固定明确叙事/宣传/花絮意图和含糊宣传默认；缺素材影响是否可完成，不反向改成宣传。自动叙事仅在用户明确允许时刻合集时降为花絮；其他缺因果叙事保留体裁只交缺口。`GenreDecision.basis` 记录 AI 意图、版本和最终裁决依据；快照绑定完整输入。泛化同义表达尚需独立素材与需求验证。
- `bind_genre_to_inventory` 将底线前的一次体裁决定绑定最终合格盘点，更新快照与受限原因，不再进行第二次模型路由，审核与底线始终使用同一体裁。
- 可见数量/仪表读数只允许逐字引用原事实；产能/性能/比例仍须逐字用户事实及来源。未给来源的数字卖点拒绝。
- 每次生成最多 `MAX_PLAN_REVISIONS=6` 次修订；原提案和失败原因用于反馈，每次再过同一套门。`rejectedAttempts/rejectionReasons/rejectionMessages` 分别保留机器原因历史、最终原因和可读中文说明。
- Provider 429 沿用既有 Retry-After 退避，耗尽不重新套预算；超时/网络/TLS/5xx 使用既有补发预算 2 次，只重发失败的独立请求，不新增等待，不换 Provider。服务失败、审核拒绝、仅缺口分开计数。
- 配方版本 `genre-recipe-2026-10-05-v2`；原任务 2 的故事版附加契约不变。源窗分配/精修、最佳镜头、声音、落库与交付仍属后续任务。

## 评测方法与结果

只读原工业冻结快照，以及任务 3 `genre-eligibility-live-2026-10-05/zh-15-silent/1` 的核验快照/25 个合格窗。不跨运行合并风险事实，不把旧未知转阴性。输入包装保存源路径和 SHA256，输出全部在当前 worktree `.footage-eval/`。

每例准备阶段固定需求定义与底线集合；三次正式运行重新盘点素材、逐片查找需求支持、判断体裁、策划和独立审核，未复用盘点支持结论。准备失败独立记在 preparation-summary，未开始的三次不算运行失败。工业库缺叙事邻镜关系或花絮风险补核验时，按任务 3 的现行门报告零合格，不为提高产出率改门。

续做复核修复了需求支持 Schema 错加 `items` 字段的问题，支持索引由代码枚举约束；明确体裁不再请求一个被忽略的 AI 意图，未写明体裁才由模型理解意图/信息充分性，直接否定的体裁词不作为正向意图。Provider 初期出现 HTTP 402，诊断输出保留，4xx 不重试、不换服务。可用 `--planning-preparation` 续跑成功准备阶段，严格校验本轮完整输入相同，保存来源和哈希，三次仍独立盘点及查找支持。

第一轮完整续跑又复现了零支持误判与审核被自由缺口污染：英文 30 秒的一次把可见机器运作判成缺自动化；历史宣传的标题审核受到提案自行报告的缺口影响。当时将对账前移到审核前，对零支持需求补对账一轮；最终方案随后替换为下述全库固定键逐对判定，不再依赖稀疏补查。可见数量的截句仅在逐字原文前缀时补为完整锚点，性能数字不补；仍通过全部门。修订预算校准为代码参数 6 次。未复用旧支持结果，未改变任务 3 底线规则。

续做诊断轮再次发现：合法索引不等于支持语义，批检索会漏掉已存在的检查画面；抽象口播、片头片尾和无配音约束仍可能被模型提成必需画面。诊断轮已主动停止，不作为完整交付评测。最终方案用请求需求枚举过滤编辑参数，并用逐需求 × 逐片段绑定替代跨批检索/补查，重新准备需求定义、独立跑三次。原中断轮及 HTTP 402 诊断均保留，不择优拼接为通过结果。

逐对独立请求诊断中，Provider 并发高峰耗尽既有退避后返回 HTTP 429；该轮主动停止，未完成的用例不作为交付数据。最终保留全库逐对判断但每六个片段组成固定键完整判定批次，以减少不必要请求数，不降低覆盖、放宽底线或另套 429 预算。正式完整评测使用 `--workers 2`，全部诊断保留，不择优拼接。
